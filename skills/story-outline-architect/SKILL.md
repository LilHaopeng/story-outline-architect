# 小说大纲架构师

把大纲做成可执行的故事模型，而不是事件摘要。基本叙事单元是：

`Goal → Conflict → Choice → Cost → Consequence → New State`

人物选择必须产生代价，代价必须改变后续可用的状态；世界规则、偶发事件或他人行动可以触发剧情，但不能替代主要人物持续作出选择。

先保存作者想写的具体体验，再用人物、事件与后果实现它。结构校验通过之后，仍需检查读者的期待是否得到积累、变化与回应。

## 工作边界

- 只负责构思、大纲、审计、修订与版本锁定。用户要写正文时，交给适用的写作 Skill。
- 先盘点用户材料与现有项目结构。用户原稿、已确认设定和锁定版本是权威；未知项写 `[待确认]`，不得为了填表杜撰。
- 不直接改写源大纲或锁定文件。新方案写入工作文件；涉及既有核心设定、终局或已锁章节时，先做影响分析并取得确认。
- 若用户预先提供世界观，世界硬规则、制度、势力和开篇正典状态由该世界观拥有；本 Skill 只引用、选用冲突与种子并规划后果，不另造一套相互竞争的设定。
- 现有 `story-*` 项目继续使用 `设定/`、`大纲/`、`追踪/`、`正文/` 作为权威目录。若 `$story-codex-core` 可用，修改已有项目文件前先运行其 preflight。
- “Concept Architect”等名称表示顺序执行的审查视角，不等于已经调用多个 Agent。只有用户明确要求多代理或并行审查时才委派。

## 世界观输入兼容

先判断世界观输入属于哪一种：

1. **版本化接口**：优先读取 `设定/世界观/15_大纲接口.md`，再读取其索引、硬规则、当前状态以及被选中的 `RULE/CON/SEED` 来源文件。
2. **结构化设定但无接口**：只读盘点文件，提取来源、正典状态、规则、时代危机、结构冲突、人物入口与开放问题，写入 `大纲/世界观引用.md`；不要为了适配本 Skill 强制迁移原文件。
3. **零散笔记或对话设定**：区分用户确认事实、世界内传闻与模型假设；未确认内容标为 `open`。若设定复杂到需要制度、势力或状态建模，先建议或调用 `$story-world-architect` 完成交接。
4. **无世界观输入**：只在 Story DNA 中建立支撑当前故事所需的最小临时约束，标记为 `provisional`；不要顺手生成百科式世界观。

世界观存在时执行以下契约：

- 创建 `大纲/世界观引用.md`，固定世界观来源、版本/状态、接口文件、正典基准时间、锁定规则、选用冲突、选用种子、允许调整项、禁用假设和待确认项。它是指针与选择记录，不复制整套世界设定。
- 从世界的压力中定位主角：选择 `CON/SEED` 后再建立人物欲望、身份、债务、关系和两难；不得倒推一个只为既定主角服务的规则例外。
- Story DNA、Arc、Sequence 和 Chapter 按需引用 `RULE/CON/SEED/FAC` ID；没有稳定 ID 时先记录源文件与原文定位。
- 把大纲计划导致的未来世界变化写入 `追踪/世界状态变化.md`，不得直接写进世界观的“当前世界状态”。正文实际发生并核验后，才由世界观流程并入正典。
- 构想违反 hard 规则时只可选择：适配剧情、提出世界观变更、另开世界版本。不得静默添加一次性豁免。
- 世界观版本变化后重新执行兼容审计；若大纲已锁，必须通过 Change Request 传播，不自动刷新版本号。

## 选择模式与深度

先判断任务模式：

| 模式 | 适用请求 | 主要动作 |
|---|---|---|
| create | 从想法、梗概或设定开纲 | 自上而下建立 L0-L4 |
| expand | 已有总纲，要扩卷纲、剧情段或章纲 | 锁定上层后只扩目标层 |
| audit | 复核可行性、逻辑、中段、反转或节奏 | 只读审计，先报告再改 |
| repair | 用户已授权修大纲 | 从最高受影响层向下重算 |
| change | 修改已锁内容 | 先生成 Change Request 和影响矩阵 |
| lock | 用户确认定稿 | 严格校验后创建不可覆盖的版本快照 |

再按复杂度选择深度：

- `compact`：短篇、单线或早期探索。完成 L0-L2，合并 L3/L4，保留最少台账。
- `standard`：普通长篇。完成 L0-L4，维护状态、因果、伏笔和未闭环。
- `deep`：多 POV、悬疑、强反转、复杂制度或世界规则。按需启用完整信息/反转、压力与 L5 场景蓝图。

章节数只是参考；复杂度比篇幅更重要。不要为了“完整”强迫轻量项目维护无用文件。

## 选择故事驱动力

从用户材料判断本书主要靠什么吸引读者：关系、成长、解谜、求生、事业或其他；混合型写明主次。目标读者与平台影响类型承诺，不以“男频/女频”直接决定生成方法。

创建或修复核心体验、人物、主辅线、高潮和阶段循环时，读取 [story-generation.md](references/story-generation.md)，只启用与本次范围有关的方法：

- L0：保存创作初衷、代表性期待场面、简短梗概和核心追读问题；悬念与主题分别表述。
- L1-L2：从人物经历与信念生成选择；按主导驱动力组织主辅线、关键高潮、人物高光和阶段成果。
- L3-L4：把积累、触发、选择、回报与后果落实到事件；关系变化与成长成果由后续节点继续使用。

详细记录优先写入现有 DNA、架构、Arc/Sequence 和台账；轻量项目按需使用短段落，不为每种方法新建文件。已有角色设定继续拥有稳定事实，大纲引用它并规划行动。

## 六层模型

| 层级 | 回答的问题 | 默认产物 |
|---|---|---|
| L0 Story DNA | 这是谁的什么故事，最终回答什么 | `大纲/00_故事DNA.md` |
| L1 Story Architecture | Plot、Character、Conflict、Information、Theme 如何同步推进 | `大纲/01_故事架构.md` |
| L2 Arc Architecture | 每个大弧线造成什么不可逆变化 | `大纲/故事弧/ARC-*.md` |
| L3 Sequence | 2-6 章左右的局部问题如何提出、升级、解决并留后果 | `大纲/剧情段/SEQ-*.md` |
| L4 Chapter Outline | 本章功能、选择、代价、信息与章末推动力 | `大纲/细纲_第XXX章.md` |
| L5 Scene Blueprint | 场景内权力、行动、转折如何变化 | `大纲/场景/*.md`，仅对近期章节按需创建 |

具体字段、兼容目录和台账格式见 [artifact-contract.md](references/artifact-contract.md)。创建或扩写任何层级前读取该文件。

## 分阶段工作流

### 0. 盘点与可行性预检

1. 列出已有来源、当前权威文件、已锁内容、相互矛盾的版本与缺失材料。
2. 检查是否有世界观索引、接口、锁定 manifest、当前状态或其他设定来源；有则先建立 `大纲/世界观引用.md` 并固定所用版本。
3. 确认目标读者/平台、体量、类型承诺、主导驱动力、用户硬约束和本次只做到哪一层；能从材料可靠推断的不要重复询问。
4. 给出简短预检：`可进入大纲 / 需先补关键决策 / 当前设定不可行`。把世界硬规则问题、世界—大纲接口问题与故事结构问题分开。
5. 初始化空目录时可运行 `<skill-dir>/scripts/init_outline_project.py`；它只创建缺失文件，不覆盖现有内容。先解析本 Skill 的实际目录，不要假设项目根下存在 `scripts/`。

```text
python <skill-dir>/scripts/init_outline_project.py --root <项目根> --title <书名> --mode <compact|standard|deep>
```

### 1. L0：冻结故事基因

形成 Story DNA，并做第一次压力测试：核心目标是否能支撑预期篇幅；主角欲望、深层需求、阻力、价值矛盾、类型承诺和终局是否互相作用；独特机制是否能持续产生选择。已有世界观时，核心阻力、独特机制和持续引擎必须能追溯到已选 `CON/SEED/RULE`，并说明人物入口；不强迫使用世界观提供的每个种子。

将创作初衷写成具体的处境、关系或感受，并保存一个代表性期待场面；只有模型提出的场面应标明“候选，待用户确认”。用约 100 字的核心故事说明人物、触发、追求与主要阻力，再提出读者持续等待回答的问题。这里保存体验锚点，不提前排章节。每次上层修订后核对初衷与核心体验是否仍成立；需要改变已确认体验时展示取舍。

向用户展示 L0 与关键待确认项。未确认前不批量展开章节。若用户明确要求不中断地先出全案，可继续，但所有产物标为 `draft`，不得锁定。

### 2. L1-L2：架构与故事弧

1. 建五轨总表，并把人物弧嵌入 Plot，而不是另写一条互不影响的成长线。
2. 从终局反推主要 Arc。每个 Arc 都要有起始状态、目标、主要阻力、升级、关键选择、代价、不可逆后果和结束状态。
3. 已有世界观时，Arc 写明读取的 RULE/CON/SEED 和拟议的世界状态变化；终局不得默认世界会在冲突解决后自动复位。
4. 只为关键转折维护因果依赖，不为每个微小动作造图。因果表即 Story Graph 的权威来源，需要可视化时再派生图。
5. 用户确认主线、终局和 Arc 顺序后再进入批量下钻。

展开架构时，先引用或补足主要人物的决策依据：关键经历、形成的信念、渴望、恐惧、底线及惯用应对。参考角色只提取行为机制；标签、职业和出身都需要通过本项目的行动解释。

对本次范围内的关键高潮，先指定要回应的期待和高潮后的变化，再反推必要积累、触发与选择，最后按时间顺序检查动机和信息是否成立。主辅线用同一事件连接外部结果与体验变化；成长/事业故事同时规划阶段成果、保留收益、新行动与新压力，卷与 Arc 可按项目结构映射。

### 3. L3-L4：剧情段与章纲

1. 每个 Sequence 围绕一个可回答的问题；其结尾必须改变目标、规则、权力、关系、资源或信息中的至少一项。
2. 先做一个代表性 Sequence 和 1-3 章样例，校准粒度；确认后再按批次扩展。
3. 长篇采用滚动视野：近期 5-10 章详细并冻结，中期按 Sequence 规划，远期只保留 Arc 锚点。不要一次生成整部小说的场景级细纲。
4. L4 保留现有 `story-long-write` 所需的核心事件、目标情绪、钩子和字数字段，同时增加选择、代价、状态与信息字段。
5. 章纲涉及世界规则、制度、势力或知识边界时读取已固定版本；变化只写入大纲状态和 `追踪/世界状态变化.md`，不直接改世界正典。

利用既有字段落实生成方法：`新信息` 记录读者与人物的认知差，`状态变化` 记录具体关系或成果变化，`目标情绪` 写清体验的进入与退出，`爽点/情绪回报` 说明此前期待及本次回应。安静章可积累信任、技能或决策条件；关键节点才展开完整高潮卡。若多个节点只是重复受挫或清空收益，先重算推进方式。

### 4. L5：按需场景蓝图

只有在下一步要写正文、复杂谈判/推理/动作需要编排，或章纲仍不足以执行时才创建。默认只覆盖接下来 1-3 章；不得提前把全书锁成场景清单。

### 5. 七视角审计

依次执行 Concept、Story、Character、Conflict、Outline、Logic、Story Doctor 七个审查视角。读取 [audit-rubric.md](references/audit-rubric.md)，先列证据与问题，再给修订；不得把同一上下文中的顺序自审描述成独立多审稿人结论。

硬性逻辑阻断项优先于分数。已有世界观时额外检查版本漂移、无效 RULE/CON/SEED 引用、角色知识越权、未登记规则例外、当前状态与拟议状态混写。自动脚本只验证结构、ID、父子引用、世界观引用字段和占位符，不声称能判断文学质量。

另做体验审计：创作初衷是否仍有对应情节，高潮积累是否发生质变，人物高光是否有行为依据，回报是否回应此前期待，阶段循环是否保留成果并改变后续行动。按作品调性判断，避免把依赖反转、打脸、受虐或更大场面写成通用要求。需要检查新增 L0 体验字段的存在与非空状态时，可加 `--generation-checks`；结果仅为结构提示，不影响旧项目默认校验，也不证明情绪效果。

### 6. 修订与锁定

按 `世界观引用 → L0 → L1 → L2 → L3 → L4 → L5 → 台账` 的顺序向下传播修改。涉及锁定内容时读取 [change-control.md](references/change-control.md)，先给影响范围与最小改动方案。若变更源于世界观新版本，先比较接口差异，再更新引用和所有受影响节点。

锁定前运行：

```text
python <skill-dir>/scripts/validate_outline.py --root <项目根> --scope <dna|architecture|arc|sequence|chapter> --strict
```

只有用户明确确认锁定后，才运行：

```text
python <skill-dir>/scripts/lock_outline.py --root <项目根> --version v1.0 --scope chapter --note "用户确认的大纲版本"
```

### 7. 汇编与 DOCX 最终交付

当用户要求的本次大纲范围已经完成、通过相应审计并准备最终交付时，读取 [docx-delivery.md](references/docx-delivery.md)，使用 `$documents` 将全部当前有效大纲信息排版成一个 DOCX。阶段性讨论和滚动修改继续以 Markdown 为权威，不要求每个批次都重做 DOCX。

最终 DOCX 是指定大纲版本的阅读版快照，不取代 `大纲/` 与 `追踪/` 的源文件。必须：

1. 盘点并对账世界观引用、Story DNA、故事架构、全部有效 Arc/Sequence/Chapter、按需场景蓝图及所有启用台账；不得用摘要替代用户要求保留的细纲信息。
2. 在 DOCX 中标明交付范围、最高完成层、活动视野、大纲版本、世界观来源/版本、未完成层与覆盖清单；草案必须醒目标记 `draft`。
3. 按层级和阅读任务重新排版，提供目录、稳定标题、页眉页脚、可读表格与清晰分页；不得把多个 Markdown 文件无区分地顺序拼接。
4. 按 `$documents` 的要求完成依赖加载、DOCX 创建、逐页 PNG 渲染、100% 视觉检查和必要的修订重渲染。
5. 默认只向用户交付最终 `.docx`；PNG、PDF 和 QA 日志只作内部验证，除非用户另行要求。

## 交付要求

每次完成一个阶段，都给用户：

1. 当前结论和已完成层级。
2. 新建或修改的文件链接。
3. 阻断问题、待确认项和下一层会受影响的内容。
4. 使用的世界观来源/版本、选用的冲突与种子，以及未采用内容；无世界观时说明临时约束。
5. 实际验证范围：结构校验、世界观兼容审计、语义审计、版本快照分别说明，不能把文件存在等同于大纲可行。
6. 本次任务最终完成时，交付一个包含全部当前有效信息的排版版 DOCX，并报告其大纲版本、世界观版本、汇编覆盖范围与逐页视觉 QA 状态。

不要用平均分掩盖核心缺陷；不要为了提高指标机械塞选择、反转或状态变化；不要让主题变成角色说教。所有指标都是定位问题的证据，不是替代编辑判断的目标。
