# 大纲 DOCX 最终交付契约

仅在本次大纲任务已经完成并准备最终交付时读取。`大纲/` 与 `追踪/` 中的 Markdown 继续作为可编辑权威来源；DOCX 是指定版本、范围和滚动视野的阅读版快照。

## 1. 触发与状态

- `create / expand / repair / change / lock`：完成用户要求的层级与范围后生成一个 DOCX。
- `audit`：DOCX 应收录审查范围内的有效大纲、审计证据、问题分级和修订顺序，不得只交付脱离原结构的简短意见。
- 锁定交付先严格校验并创建版本快照，再从同一快照汇编 DOCX。
- 用户要求阶段性阅读版时可以生成草案，但必须标注 `draft`、最高完成层、活动视野、未完成层和待确认项。
- DOCX 完成后在 `大纲/工作状态.md` 记录文件路径、版本、完成层级、生成日期和 QA 状态；不得用 DOCX 覆盖或替代 Markdown 源文件。

默认路径：

```text
{项目根}/交付/{项目名}_小说大纲_{版本}.docx
```

没有正式版本时使用 `draft-YYYYMMDD`，不得冒充锁定版本。

## 2. 汇编前对账

先建立汇编清单，逐项记录 `源文件/对象 → DOCX 章节 → 状态 → 是否收录 → 未收录理由`。至少盘点：

- `大纲/工作状态.md`、锁版 manifest、兼容总纲和卷纲。
- `大纲/世界观引用.md` 及使用的世界观接口/版本；不要把整套世界观重复进大纲 DOCX，只收录本书实际引用的规则、冲突、种子和约束摘要。
- Story DNA、故事架构与五轨、全部有效 ARC、SEQ、CH 和按需 SC。
- 当前已启用的创作初衷、期待场面、核心追读问题、驱动力、人物决策依据、高潮与回报规划、卷/Arc 阶段成果和承接；在所属层级收录，不用新增字段要求反向修改旧锁版来源。
- `追踪/大纲状态.md`、`世界状态变化.md`、`因果依赖.md`、`未闭环.md`、`伏笔.md`、`信息与反转.md`、`压力曲线.md`、`时间线.md`、`角色状态.md`、`大纲变更.md` 中实际启用的内容。
- 审计报告、变更请求、开放问题、研究项以及影响当前大纲的用户确认记录。

active、reviewed、locked 内容不得静默省略。retired、superseded、被拒方案和旧版本可进入附录或只在变更历史中登记，但必须与当前有效大纲明确分隔。

在成稿后进行数量与顺序对账：ARC、SEQ、CH、SC、EVT、F、T、LOOP、S、CR 以及世界观 RULE/CON/SEED 引用的 ID 集合必须与源材料一致；章节编号、父子关系和排序不得因排版而改变。

## 3. 建议文档结构

按实际最高完成层调整，但所有已完成层都要收录：

1. 封面：项目名、文档名、大纲版本、状态、最高完成层、活动视野、世界观版本、生成日期。
2. 编制说明：权威来源、交付范围、结构策略、未完成层、草案/锁定声明和阅读方式。
3. 故事总览：Story DNA、一句话命题、类型承诺、核心体验、持续引擎和可行性压力测试；收录来源中实际存在的创作初衷、期待场面、核心追读问题与驱动力。
4. 世界观引用：来源/版本、本书锁定规则、选用冲突与种子、禁用假设、开篇正典状态。
5. 故事架构：书级目标、开篇/终局状态、五轨总表、人物×情节矩阵和主支线契约，以及实际启用的人物决策依据与关键节点概览。
6. 故事弧：按 ARC 顺序完整收录功能、目标、阻力、选择、代价、不可逆后果、状态与依赖，以及已规划的高潮积累、回报、高光和阶段承接。
7. 剧情段：按所属 ARC 和 SEQ 顺序收录驱动问题、升级、选择、后果及章节分配。
8. 章纲：按 CH 数字顺序完整收录，不得为了缩短 DOCX 删除核心事件、选择、代价、信息、状态变化、钩子或连续性输入。
9. 场景蓝图：仅收录实际存在的 SC，并按章节归组。
10. 状态与因果台账：核心状态、世界状态变化、关键事件依赖和时间线。
11. 信息、伏笔与未闭环：知识状态、反转、伏笔、承诺、角色状态和压力曲线。
12. 审计、变更与版本：S0–S3 问题、修订记录、CR、锁版信息和遗留风险。
13. 汇编覆盖清单与来源附录。

开篇总览可以概括，但后续章节必须保留完整有效大纲信息；不得以“篇幅太长”为由只交付摘要版，除非用户明确要求精简。

## 4. DOCX 排版规则

使用 `$documents`，并遵循它在执行时的最新完整规范：加载工作区依赖、执行一次 artifact-operation 标记、选择/继承模板或设计预设、在可写目录构建、渲染并逐页检查。

- 有用户模板时以模板为设计权威；没有时按 `$documents` 的模板选择流程处理，未选模板则优先使用适合“长篇结构手册/参考指南”的紧凑参考型预设。
- 使用真实 Word 标题样式区分 L0–L5、ARC、SEQ、CH 和 SC；长文档应有目录、页码、项目名/大纲版本页眉或页脚。
- ARC、SEQ 和 CH 使用稳定且可扫描的重复版式，但不要把长段叙述塞进窄表格。总表用于比较，详细内容用标题、定义块、项目符号和短段落。
- 大型五轨表、人物矩阵或时间线可使用横向分节、拆表与重复表头；不得用小字号和压缩边距强塞。
- 表格必须有明确列宽、自动增长行高、足够单元格内边距和合理对齐；跨页后保持标题/表头与顺序可识别。
- 章纲之间使用清晰分页规则，避免章标题孤立在页尾；也避免每一章强制新页造成大量空白，按实际长度控制分页。
- `draft`、阻断项、待确认项和世界观兼容风险使用克制且一致的视觉标记。
- 不在 DOCX 中泄漏工具引用标记、内部路径噪声或 QA 命令输出。

## 5. 构建与视觉验收

1. 固定本次大纲与世界观版本；锁定交付运行严格校验，草案则保留显式未决清单。
2. 按汇编清单生成 DOCX，并再次抽取/核对标题层级、对象 ID、章节顺序、父子引用、表格和版本元数据。
3. 使用 `$documents` 包内的 `render_docx.py` 生成每页 PNG。
4. 在 100% 视图检查每一页：缺字、乱码、溢出、重叠、孤标题、异常空白、破表、章纲断裂、页眉页脚错位、行距和单元格拥挤。
5. 修复后重新渲染；任何布局敏感修改后都必须复核全部受影响页面，最终交付以最后一次渲染为准。
6. Windows 环境若出现控制台 `UnicodeDecodeError`，先设置 `PYTHONUTF8=1` 和 `PYTHONIOENCODING=utf-8`，再以 PNG/PDF 是否实际生成及逐页检查结果判断，不要只凭控制台报错认定失败。
7. 只有 LibreOffice/soffice 确实缺失时才允许跳过渲染；此时做结构 QA，并在最终回复明确说明未完成视觉 QA。

验收必须同时满足：

- 大纲版本、世界观版本、最高完成层和活动视野在封面、正文与覆盖清单中一致。
- 全部当前有效层级、对象和启用台账已收录或有明确未收录理由。
- ARC→SEQ→CH→SC 层级与编号顺序无丢失、重复或错位；世界观引用仍有效。
- 所有页已检查，无剪裁、重叠、乱码、破表、异常分页或明显排版缺陷。
- 锁定版没有 `[待确认] / TODO / TBD`；草案中的未决项被集中列出并醒目标识。
- 最终 `.docx` 可正常打开且非空；QA PNG/PDF 不作为默认交付物。

## 6. 最终回复

默认只交付最终 DOCX，并简要报告：大纲版本、世界观版本、最高完成层、ARC/SEQ/CH 数量、未覆盖内容和逐页渲染 QA 结果。按 `$documents` 的交付规范对最终 DOCX 使用一次 output 文件引用；不要逐章重复引用，也不要链接内部 QA 图片，除非用户要求。
